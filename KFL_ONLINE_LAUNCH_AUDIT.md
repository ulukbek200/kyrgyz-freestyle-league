## 2. Блокеры и риски

### REGISTRAR отсутствует

`apps/api/prisma/schema.prisma:29` содержит только `ADMIN`, `MODERATOR`, `ATHLETE`. Те же роли перечислены в `auth.ts` и схемах создания/изменения пользователя в `adminManagement.ts`.

Весь `adminManagement` закрыт `allow('ADMIN')`, `/admin/session` отдельно требует ADMIN; результаты и изменение рейтинга также защищены ADMIN. Администратор может создать отдельного пользователя, но **не REGISTRAR**. MODERATOR не является регистратором: он тоже не может пользоваться регистрацией в текущей админке. Выдать ADMIN вместо REGISTRAR означало бы разрешить изменение результатов — так делать нельзя.

Предлагаемая минимальная матрица для реализации:

| Операция | ADMIN | REGISTRAR |
| --- | --- | --- |
| Вход и ограниченная рабочая панель | Да | Да |
| Просмотр минимального реестра, категорий, клубов и тренеров для регистрации | Да | Да |
| Создание профиля спортсмена и загрузка его фото | Да | Да |
| Изменение/удаление существующих профилей | Да | По умолчанию нет; отдельное правило при необходимости |
| Регистрация существующего спортсмена в турнир | Да | Отдельное право, если требуется; не выдавать весь доступ к турнирам |
| Изменение результатов, рейтинга, сетки, турниров, сезонов | Да | Нет, серверный 403 |
| Создание пользователей, изменение ролей и блокировка | Да | Нет |

Нужны: добавочная enum-миграция `REGISTRAR` без удаления данных; изменение типов JWT и валидаторов; разделение прав по endpoint вместо расширения общего `allow('ADMIN')`; отдельное меню/маршруты; сохранение auditLog.userId; API-тесты прямого обхода UI, эскалации роли и отзыва прав. Уже существующих ADMIN автоматически не понижать. Все пути записи результатов, правил рейтинга, пересчёта и турнирной сетки должны остаться ADMIN-only.

### Фото потеряются без постоянного хранилища

`apps/api/src/adminManagement.ts:19` жёстко задаёт `<workspace>/.local/uploads`. В проверенной папке **26 файлов, 10 504 535 байт**. PostgreSQL хранит ссылки, а не эти файлы. Копирование только БД не перенесёт фотографии.

В Render обычная файловая система временная. Минимальный вариант для текущей архитектуры: persistent disk на `/opt/render/project/src/.local/uploads`, если сервис развёрнут из корня monorepo. Предпочтительнее сделать `UPLOAD_DIR` настраиваемым и использовать `/var/data/uploads`, либо подключить объектное хранилище. Сейчас `UPLOAD_DIR` кодом **не поддерживается**. Диск ограничивает сервис одним экземпляром и исключает zero-downtime deploy. [Render Persistent Disks](https://render.com/docs/disks).

Нужно отдельно перенести файлы с сохранением имён, сверить контрольные суммы и проверить ссылки. Для S3-подобного хранилища понадобится адаптер загрузки и перенос существующих объектов. Старые локальные `/uploads/...` frontend умеет направлять на новый API; для прочих абсолютных локальных/HTTP URL нужна отдельная сверка. Не заменять ссылки в БД массово без отчёта.

### Proxy, HTTPS, health-check

- Render завершает TLS на своём балансировщике и перенаправляет HTTP на HTTPS. В Express достаточно внутреннего HTTP; не нужен самостоятельно выпущенный сертификат. Публичный `VITE_API_URL` должен быть HTTPS. [Render Web Services](https://render.com/docs/web-services).
- `configureProxy` принимает только явные IP/CIDR; значения `true` и количество hops запрещены. Не подставлять случайный диапазон или `0.0.0.0/0`. Нужно подтвердить цепочку Render-прокси, определить надёжное правило доверия и проверить IP на staging. Пока это не проверено, нельзя считать IP rate limiting готовым для Render. Неверная настройка даёт общий лимит или возможность подмены IP.
- Лимитеры используют память процесса: перезапуск сбрасывает лимит, несколько экземпляров считают независимо. Для масштабирования потребуется общий store.
- `/api/health` всегда отвечает `{status:'ok'}` без запроса к PostgreSQL. Это liveness. Добавить `/api/ready` с ограниченным по времени `SELECT 1`, ответом 503 без внутренних деталей при сбое; его использовать для проверки готовности Render. [Render Health Checks](https://render.com/docs/health-checks).
- Добавить SIGTERM/SIGINT: закрыть HTTP-сервер, дождаться текущих запросов в пределах тайм-аута, отключить Prisma.

### Переменные, секреты и первый ADMIN

Проверено без раскрытия значений секретов:

- корневой `.env` указывает на локальную `kfl_stage2_test`; `TEST_DATABASE_URL` сейчас также указывает туда. Эту настройку нельзя переносить в облачный runtime; тесты должны использовать отдельную базу;
- `apps/web/.env.local` задаёт `VITE_API_URL=http://localhost:4000/api`. В production это адрес компьютера посетителя, а не сервера KFL;
- `.gitignore` скрывает `.env` и `.local/`, но не все `.env.*`. Добавить правила `.env.*`, `**/.env.*` с исключением безопасных example-файлов перед будущим push;
- production должен получить новый случайный JWT_SECRET и уникальный сильный пароль администратора. Не переносить локальные тестовые учётные данные;
- `prisma/seed.ts:7` вызывает массовые `deleteMany`, затем создаёт демонстрационные записи. **Не использовать seed для production**;
- отдельного безопасного bootstrap-admin скрипта нет. Нужна идемпотентная процедура: создать первого ADMIN только явно, без удаления записей/сброса паролей существующих пользователей; секрет вводить через защищённое окружение;
- JWT хранится frontend в localStorage: это существующий риск при XSS. Не добавлять произвольный HTML, проверить CSP на Vercel; CORS не заменяет серверную проверку ролей;
- не переносить локальную настройку `NODE_TLS_REJECT_UNAUTHORIZED=0`, если она присутствует в окружении разработчика.

## 3. Конкретные настройки Render (после согласования запуска)

Создать отдельные staging Web Service и PostgreSQL, сначала проверить на них. Для постоянного запуска подобрать тариф с необходимыми бэкапами/диском; стоимость в этом аудите не рассчитывалась. Отключить Auto-Deploy до разрешения запуска. Создание Web Service само запускает первый deploy — на данном шаге его не создавать.

| Поле | Значение |
| --- | --- |
| Runtime | Node |
| Root Directory | Корень репозитория, не `apps/api` |
| Build Command | `npm ci --include=dev && npm --workspace apps/api run db:generate && npm --workspace apps/api run build` |
| Start Command | `npm --workspace apps/api start` |
| Pre-Deploy Command | После проверки БД/бэкапа и отдельного разрешения: `npm --workspace apps/api run db:deploy` |
| Health Check Path | Сейчас `/api/health`; после реализации readiness — `/api/ready` |
| Auto-Deploy | Off до утверждения |

Зафиксировать одну поддерживаемую версию Node в проекте и на платформах; в package.json сейчас нет engines. Не переносить с Windows готовые `node_modules` или Prisma engine: generate выполняется на Render/Linux. Dev dependencies нужны для TypeScript, Prisma CLI и текущего migration-wrapper на tsx.

Pre-deploy для миграций доступен у платных Web Services; при отсутствии этой возможности использовать отдельно контролируемую команду миграции, не прятать её в build/start. [Render Deploys](https://render.com/docs/deploys#pre-deploy-command).

Переменные Render:

```dotenv
NODE_ENV=production
DATABASE_URL=<секретная строка отдельной облачной PostgreSQL>
JWT_SECRET=<новый случайный секрет минимум 32 символа>
WEB_ORIGIN=https://<основной-домен-frontend>
TRUSTED_PROXIES=<только подтверждённые доверенные IP/CIDR>
```

`PORT` оставить платформе. Для нескольких frontend-origin перечислять их без пробелов, путей и завершающих `/`. Не разрешать все `*.vercel.app`; preview окружение должно работать со staging API/БД. `DATABASE_URL` и JWT_SECRET никогда не помещать в `VITE_*`.

PostgreSQL разместить в том же аккаунте/регионе, использовать Internal Database URL. TLS можно требовать параметром `sslmode=require`; не добавлять второй `?`, если URL уже содержит параметры. Внешний доступ ограничить; для внешнего подключения использовать полный DNS hostname и TLS. Настроить бэкапы и проверить восстановление на отдельной базе. [Render PostgreSQL](https://render.com/docs/postgresql-creating-connecting).

## 4. Vercel

Не менять существующий проект до сверки его Root Directory и production commit. Воспроизводимый вариант из корня monorepo:

| Поле | Значение |
| --- | --- |
| Framework | Vite |
| Root Directory | Корень репозитория |
| Install Command | `npm ci --include=dev` |
| Build Command | `npm --workspace apps/web run build` |
| Output Directory | `apps/web/dist` |
| Production env | `VITE_API_URL=https://<backend>.onrender.com/api` |

Если существующий Root Directory — `apps/web`, путь output должен быть `dist`, а команды/доступ к корневому workspace надо согласовать с этим режимом. Не смешивать два варианта. Не использовать корневой `npm run build` для Vercel: он также собирает backend.

Переменная VITE_API_URL встраивается при сборке: после разрешённого изменения понадобится новый deploy frontend. Для BrowserRouter нужен SPA fallback; в выбранном корне проекта подготовить:

```json
{
  "rewrites": [{"source": "/(.*)", "destination": "/index.html"}]
}
```

Проверить прямое открытие и обновление `/events/:id`, `/athletes/:id`, `/admin`. Конфиг выше — предложение, файл в текущем проекте не создан. [Vite on Vercel](https://vercel.com/docs/frameworks/frontend/vite).

## 5. Миграции и перенос данных

Миграции не являются полностью «пустыми DDL»: возрастная миграция заполняет даты рождения и категории; независимые турниры создают регистрации из истории со статусом NEEDS_REVIEW; индекс единственного активного сезона остановится при конфликтующих данных. История миграций должна переноситься вместе с выбранным снимком БД. Нельзя просто считать миграции применёнными через resolve без сверки схемы.

Два отдельных сценария:

1. **Новая пустая облачная БД:** проверить hostname, database, отсутствие чужих таблиц → применить проверенные migrate deploy → безопасно создать первого ADMIN и необходимые настройки, без demo seed.
2. **Перенос реальных локальных данных:** определить, какие записи действительно нужно переносить → согласовать окно остановки записи → backup БД и uploads → пробное восстановление в новой изолированной БД → проверить `_prisma_migrations`, счётчики и связи, фото → применить только отсутствующие проверенные миграции → переключить API после подтверждения. Не совмещать restore полного дампа с предварительным созданием тех же таблиц миграциями.

Команды из корня проекта. Это инструкция, не выполненные удалённые действия. DATABASE_URL заранее задаётся защищённым способом для точно выбранной базы; не вставлять секреты в чат/журналы:

```sh
# Локальная/CI подготовка без применения миграций
npm ci --include=dev
npm --workspace apps/api run db:generate
npm run db:validate
npm run typecheck
npm run build
npm test

# Проверка истории выбранной БД (только после проверки назначения подключения)
npm --workspace apps/api exec -- prisma migrate status --schema prisma/schema.prisma

# Только после разрешения, бэкапа и staging-прогона
npm --workspace apps/api run db:deploy
npm --workspace apps/api start
```

Пример backup/restore с предварительно настроенными libpq service definitions и защищённым файлом паролей; значения `kfl_source` / `kfl_restore_test` должны указывать на явно проверенные базы:

```sh
pg_dump --dbname="service=kfl_source" --format=custom --file=kfl-before-launch.dump
pg_restore --list kfl-before-launch.dump
# Только в НОВУЮ ПУСТУЮ тестовую БД после проверки её назначения
pg_restore --dbname="service=kfl_restore_test" --no-owner --no-privileges --exit-on-error kfl-before-launch.dump
```

Не выполнять `migrate reset`, `db push --accept-data-loss`, demo seed, `pg_restore --clean` на базе с существующими данными. Для production применять `migrate deploy`, не `migrate dev`; эта команда не заменяет проверку расхождений схемы. [Prisma: applying migrations](https://www.prisma.io/docs/orm/migrations/applying-a-migration).

## 6. Порядок оставшейся работы

1. Получить адрес frontend, параметры Vercel и сведения о репозитории/commit; проверить реальные запросы без изменения production.
2. Локально реализовать REGISTRAR и отрицательные тесты доступа, readiness/shutdown, настройку хранения, проверки production env, безопасный bootstrap-admin и примеры deploy-конфигурации.
3. Создать staging только после разрешения действий в облаке. Настроить PostgreSQL, хранилище, proxy и HTTPS-origin; прогнать миграции и регистрацию/фото/вход/403/отзыв ролей.
4. Проверить сохранность фото после redeploy, восстановление бэкапа, отсутствие запросов к localhost, CORS preflight с Authorization и отказ доступа к данным по запрещённой роли.
5. Представить фактические staging-результаты, конкретный набор изменений и план переключения для финального подтверждения production.

До этих шагов заявлять готовность REGISTRAR и полноценного облачного запуска нельзя. В этом проходе создан только данный отчёт; рабочие данные и удалённая инфраструктура не изменены.
