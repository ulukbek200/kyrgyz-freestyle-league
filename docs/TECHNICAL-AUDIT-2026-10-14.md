# KFL — технический аудит, 14 октября 2026

## A. Общий статус

**Проект собирается, основная новая архитектура работает, но к production пока не готов.** Подтверждены сохранение независимых спортсменов, регистрация в турниры, расчёт результатов и история чемпионства. Найдены ошибки проверки актуальных прав, входных данных и публичного интерфейса. Штатная браузерная регрессия не зелёная.

По ТЗ аудит выполнен **без исправлений исходного кода**. Не изменялись схема, миграции и исходные тесты. Созданы диагностические сценарии, логи, скриншоты и этот отчёт; сборка обновила генерируемый `dist`, штатные браузерные тесты — свои скриншоты. ### Prisma, связи и сохранность

Применены и сверены:

1. `202610120001_baseline`.
2. `202610120002_single_active_season`.
3. `202610130001_age_divisions`.
4. `202610130002_independent_athletes_tournaments`.
5. `202610140001_event_banner`.

`TournamentParticipant` связывает спортсмена и турнир; уникальность `(eventId, athleteId)` защищена БД (`schema.prisma:369`). Для рейтингов без сезона существует дополнительный partial unique index `Ranking_league_weight_athlete` в SQL-миграции, поэтому nullable seasonId не оставляет эту уникальность только на уровне приложения. Триггер сопоставляет новых участников схватки с регистрациями и дивизионом. Ветки для старых данных с `ageDivision IS NULL` намеренно допускают архив: это не универсальная валидация всех legacy-записей.

Удаление Event с Match или TournamentParticipant блокируется `Restrict` (`schema.prisma:185,366`). Удаление турнира не каскадирует на Athlete. EventWeightClass каскадирует только таблицу связей. Матчи и регистрации ссылаются на Athlete через `Restrict`; приложение использует смену статуса профиля вместо удаления. У рейтингов/снимков есть Cascade от спортсмена/веса/сезона: будущие операции удаления этих сущностей требуют отдельной проверки сохранности, даже если текущий интерфейс их не предлагает.

В `RankingSnapshot.eventId` и `Championship.matchId` нет relation/FK; `matchId` уникален, но это не проверка существования матча — B17. Старые Season и AthleteSeasonRegistration сохранены для истории, а не удалены вместе с меню.

## B. Найденные ошибки и риски

Ниже 21 пункт: 3 High, 15 Medium, 3 Low. Critical по выполненным проверкам не подтверждены. Приоритет эксплуатационных рисков — оценка аудита; уровни npm advisory приводятся отдельно. Статические риски не выдаются за воспроизведённые сбои.

### B01 — High: понижение роли не отзывает полномочия JWT

- **Где:** `apps/api/src/auth.ts:24–30`, `apps/api/src/adminManagement.ts:43–46`.
- **Причина:** allow проверяет роль из подписанного токена; актуальная роль БД проверяется только `/admin/session`.
- **Воспроизведение:** получить ADMIN JWT, изменить роль этого пользователя на ATHLETE в аудит-БД, вызвать session и athletes старым токеном. Получено соответственно **403 и 200**.
- **Затронуто:** защищённые маршруты за общим authenticate/allow. Старые права сохраняются до истечения токена (8 часов); обход подтверждён чтением, не массовыми изменениями данных.
- **Исправить:** единообразно проверять существование и актуальные права пользователя на каждом защищённом запросе либо использовать проверяемую версию сессии с отзывом при смене роли/пароля. Добавить HTTP-регрессию чтения и записи после отзыва.

### B02 — High: допустимый API баннер обрушает главную страницу

- **Где:** `apps/api/src/tournaments.ts:11`, `apps/web/src/UpcomingEvent.tsx:13`.
- **Причина:** API проверяет только префикс `http(s)://`; frontend вызывает `new URL` во время render без обработки исключения. onError изображения не перехватывает ошибку конструктора URL.
- **Воспроизведение:** создать ближайший будущий турнир с `bannerUrl: "http://"`. API вернул **201**; `/events/upcoming` выбрал этот турнир; браузер выдал `Failed to construct 'URL': Invalid URL`, текст `#root` — **0 символов**.
- **Затронуто:** вся публичная главная при таком сохранённом баннере. Обычная загрузка через UI генерирует корректную ссылку; воспроизведение выполнено через API.
- **Исправить:** полноценная валидация абсолютного URL/разрешённого upload path, безопасное разрешение URL на frontend, fallback и граница ошибок. Проверить уже сохранённые URL без автоматического удаления записей.

### B03 — Medium: новый результат разрешён в отменённом турнире

- **Где:** `apps/api/src/results.ts:21–34`, вызов `apps/api/src/index.ts:53`.
- **Причина:** changeResult проверяет матч и победителя, но не состояние связанного Event.
- **Воспроизведение:** отменить турнир с ещё не завершённой схваткой, отправить новый результат. Получено **200**, ожидалось запрещение операции (например, 409).
- **Затронуто:** результаты, рейтинг, чемпионство отменённых соревнований.
- **Исправить:** согласовать матрицу статусов; запретить новые результаты в CANCELLED, отдельно сохранить контролируемую возможность исправления исторического результата; проверять статус и изменять результат в согласованной транзакции с блокировками.

### B04 — Medium: поиск спортсмена по полному имени не работает

- **Где:** `apps/api/src/adminManagement.ts:68–70`, `apps/api/src/index.ts:15`.
- **Причина:** полная строка поиска сравнивается отдельно с firstName и lastName.
- **Воспроизведение:** создать Alpha с известной фамилией; поиск имени работает, поиск `Alpha <фамилия>` не возвращает запись (проверено в admin API).
- **Затронуто:** реестр, поиск участника турнира; аналогичная реализация публичного поиска найдена статически.
- **Исправить:** нормализовать пробелы, искать по токенам имени/фамилии, сохранить поиск клуба и добавить тесты кириллицы/разного порядка слов.

### B05 — Medium: будущая публикация доступна посетителям

- **Где:** `apps/api/src/index.ts:22`.
- **Причина:** фильтр `publishedAt: {not: null}` не ограничивает дату текущим временем.
- **Воспроизведение:** записать через admin API медиа с будущим publishedAt; публичный `/api/media` немедленно возвращает материал.
- **Затронуто:** публикации и главная. Наличие отдельного UI планирования не подтверждено; проблема существует в API-семантике даты публикации.
- **Исправить:** `publishedAt <= now` либо явно запретить будущую дату, если отложенная публикация не поддерживается.

### B06 — Medium: очищенное необязательное поле URL блокирует заявку

- **Где:** `apps/api/src/index.ts:24`, форма Apply в `apps/web/src/main.tsx`.
- **Причина:** optional разрешает отсутствие поля, но не пустую строку после очистки input.
- **Воспроизведение:** корректная заявка с `videoUrl: ""` / `photoUrl: ""` возвращает **400**; вариант без полей проходит.
- **Затронуто:** подача анкеты; полный сценарий ввода/очистки в браузере не воспроизводился, API-контракт проверен непосредственно.
- **Исправить:** единая нормализация пустых optional-значений перед валидацией и сериализацией; сохранять строгую проверку непустых ссылок.

### B07 — Medium: неверный enum статуса даёт 500

- **Где:** `apps/api/src/index.ts:18`.
- **Причина:** TypeScript cast строки query не выполняет runtime-валидацию, неверный enum доходит до Prisma.
- **Воспроизведение:** `GET /api/matches?status=INVALID` → **500** вместо 400.
- **Затронуто:** список матчей, логи ошибок.
- **Исправить:** валидировать все query-параметры Zod до запроса к БД; покрыть неизвестные enum/числа. Клиенту уже возвращается обобщённая ошибка без stack trace — это правильно.

### B08 — Low: публичная пагинация принимает дробную страницу

- **Где:** `apps/api/src/index.ts:15,18`.
- **Причина:** Number/Math.min/max не обеспечивают положительное целое и конечность всех параметров.
- **Воспроизведение:** `/api/athletes?page=1.5` → **200** с дробным page, а не 400. **500 этим запросом не получен.**
- **Затронуто:** стабильность контракта и переходов между страницами.
- **Исправить:** явная схема положительных целых page/limit с верхним пределом; определить поведение отрицательных/Infinity/NaN и проверить тестами.

### B09 — Low: несуществующий турнир маскируется пустым списком

- **Где:** `apps/api/src/tournaments.ts:50,75–80`.
- **Причина:** participants/results не проверяют существование родительского турнира.
- **Воспроизведение:** `/admin/events/missing/participants` и `/admin/events/missing/results` → **200 []**, карточка самого турнира — 404.
- **Затронуто:** диагностика неправильных ссылок/идентификаторов.
- **Исправить:** унифицировать поведение вложенных ресурсов с 404 родителя.

### B10 — Medium: загрузка проверяет сигнатуру, но не изображение

- **Где:** `apps/api/src/adminManagement.ts:144–151`.
- **Причина:** достаточно первых PNG/JPEG/WebP байтов; декодирование, размеры и квота отсутствуют.
- **Воспроизведение:** PNG magic bytes + произвольный мусор возвращают **201**, файл сохраняется. Настоящий PNG также проходит; >5 МБ возвращает 413.
- **Затронуто:** загрузки фото/баннеров, место на диске, повреждённые картинки.
- **Исправить:** безопасное декодирование с лимитами размеров/пикселей, переупаковка и квоты. UUID-имена, ограничение расширений, nosniff уже есть. **Выполнение JavaScript/XSS данным тестом не доказано.**

### B11 — High: нет ограничения попыток входа

- **Где:** `apps/api/src/index.ts:7,9`.
- **Причина:** rateLimit установлен только на заявки; login вызывает bcrypt при каждой попытке без ограничителя.
- **Воспроизведение:** статический анализ middleware-цепочки; массовый подбор пароля намеренно не выполнялся.
- **Затронуто:** публичная авторизация, подбор паролей и расход CPU.
- **Исправить:** ограничение по IP и учётной записи, корректный proxy trust для развёртывания, мониторинг неуспешных попыток. Не раскрывать, существует ли email.

### B12 — Medium: штатная браузерная регрессия не доходит до целевых действий

- **Где:** `apps/web/tests/admin-fixture.ts:15–18`, `apps/web/tests/admin-control.spec.ts:14`.
- **Причина:** общий `.ant-drawer-content:visible` во время анимации соответствует закрывающемуся выбору дивизиона и открывающемуся редактору одновременно; точный label «Описание» не совпадает с доступным именем необязательного поля.
- **Воспроизведение:** штатный Playwright: **7 strict-mode failures + 1 label timeout**. Проверки не отключались и не переписывались.
- **Затронуто:** доверие к регрессии фото/редактирования/турниров/адаптивности. Эти 8 падений классифицированы как **ошибки тестов**, а не 8 дефектов продукта.

### B16 — Medium: рост данных приведёт к избыточной работе API/БД

- **Где:** `apps/api/src/adminManagement.ts:49–54`, `apps/api/src/tournaments.ts:76–80`, `apps/api/src/rankingEngine.ts:12–29`, `apps/web/src/pages/admin/TournamentDetails.tsx:12–14`, `apps/web/src/pages/admin/useAdminSave.ts:11`, `apps/api/prisma/schema.prisma:194–195,370`.

### B17 — Medium: некоторые исторические ссылки не защищены FK

### B18 — Medium: зависимость с advisory и небезопасная настройка окружения

- **Где:** `package-lock.json:3669,1022,2437` — установленная цепочка prisma → @prisma/config → deepmerge-ts; диагностический процесс — `NODE_TLS_REJECT_UNAUTHORIZED=0`.

- **Затронуто:** инструменты сборки/миграций, доверие к HTTPS-загрузкам в таком окружении.
- **Исправить:** проверить безопасное совместимое обновление цепочки и перепроверить миграции; определить источник переменной окружения и включить проверку сертификатов. Не выполнять слепой `npm audit fix --force`.

### B19 — Medium: необработанные ошибки пишутся в лог целиком

### B20 — Medium: тестовая БД жёстко связана с базой ручной проверки

- **Где:** `apps/api/scripts/test-database.ts:8,17`, `apps/api/tests/postgres.test.ts`, `apps/api/tests/api.integration.ts`.

- **Исправить:** независимая TEST_DATABASE_URL с проверяемым назначением, запрет совпадения с БД приложения; явно отделить archive regression от новых сценариев. Не удалять полезные проверки legacy-истории.

### B21 — Low: крупный frontend chunk и лишние зависимости
