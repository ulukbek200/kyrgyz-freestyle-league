# KFL: этап 1 — запуск и проверка исправлений

## Окружение и команды

Скопируйте корневой `.env.example` в `.env`. Укажите собственный `DATABASE_URL`,
случайный `JWT_SECRET` длиной не менее 32 символов, `PORT` и `WEB_ORIGIN`.
Секрет можно сгенерировать локально:

```powershell
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
```

API (dev и собранный), Prisma-команды и seed читают корневой `.env` независимо от
рабочей директории. Переменные процесса имеют приоритет. В production сохраняйте
структуру workspace с корневым `package-lock.json`, используемым для поиска корня.
Отсутствующий или короткий JWT-секрет останавливает запуск; запасного секрета нет.

```powershell
npm ci
npm run db:generate
npm run db:validate
npm run typecheck
npm test
npm run build
npm --workspace apps/api start
# Или оба dev-сервера:
npm run dev
```

Production entrypoint: `apps/api/dist/src/server.js`. Фронтенд не изменён.
PostgreSQL необходимо подготовить по инструкции ниже до использования API данных.
`/api/health` проверяет HTTP-процесс, а не доступность PostgreSQL.

## Миграции: новая пустая база

Подготовлены две миграции: полная исходная схема и частичный уникальный индекс,
запрещающий два активных сезона. Поля `winnerId` и `method` остаются в `Match`;
в `MatchScore` новые поля не добавлялись.

После настройки подключения к **пустой** базе:

```powershell
npm run db:deploy
```

Миграции не создают администратора и не запускают seed. Создание первого реального
администратора — отдельная операция с собственным паролем и bcrypt-хешем.
Существующий `db:seed` предназначен только для одноразовой демонстрационной базы:
он удаляет данные лиги и устанавливает известный демонстрационный пароль.

## Существующая база без истории миграций

1. Сделайте резервную копию и проверьте процедуру на её отдельной копии.
2. Сверьте существующую схему с `202610120001_baseline/migration.sql`.
   Не запускайте baseline SQL поверх существующих таблиц.
3. Только при совпадении схемы отметьте baseline как уже применённую:

```powershell
node --import tsx apps/api/scripts/prisma.ts migrate resolve --applied 202610120001_baseline
```

4. Проверьте активные сезоны:

```sql
SELECT "id", "name", "startsAt" FROM "Season" WHERE "isActive" = true;
```

Если их несколько, администратор должен явно выбрать действующий сезон и
деактивировать остальные в транзакции. Миграция не делает этот выбор автоматически
и завершится ошибкой на дубликатах. Если схемы различаются или в базе уже есть
другая история миграций, сначала согласуйте отдельный план миграции.

5. Примените индекс командой `npm run db:deploy`.
   Если предыдущая попытка индекса завершилась ошибкой, после устранения причины
   используйте `migrate resolve --rolled-back 202610120002_single_active_season`
   через тот же Prisma runner, затем повторите deploy.

Reset, удаление таблиц и seed для существующей базы не нужны.

## Результаты, чемпионства, отмена

- `POST /api/admin/matches/:id/result` сохраняет прежний JSON-контракт и ответ Match.
- Добавлен `DELETE /api/admin/matches/:id/result`, также только для ADMIN с Bearer JWT.
  Без тела запроса. Отменяет **результат**, возвращает матч в `UPCOMING`, обнуляет
  победителя/метод/summary и удаляет счёт. Это не отмена самого события или матча.
- Матч, счёт, рейтинги, снимки событий, чемпионства, уведомление и аудит обновляются
  одной транзакцией. Строка весовой категории блокируется до завершения транзакции,
  чтобы параллельные результаты одной категории не перезаписывали расчёты друг друга.
- Чемпионство ведётся по весовой категории через сезоны, как в исходном API.
  Источник истины — завершённые титульные матчи, порядок `scheduledAt`, затем `id`.
  `wonAt` — дата матча, а не дата редактирования. Повторное сохранение не добавляет защит.
- Исправление старого результата пересчитывает всю цепочку титулов и снимки рейтинга
  сезона. Снимок события соответствует состоянию после его последней завершённой схватки.

### Старые чемпионства без matchId

В исходном seed чемпионства создавались без `matchId`; они могли не соответствовать
титульным матчам. В такой категории нельзя достоверно восстановить защиты по одному
победителю. При смешении таких записей с завершёнными титульными матчами API возвращает
409 и откатывает всю операцию. Записи не удаляются автоматически.

Перед использованием титульных результатов найдите такие записи:

```sql
SELECT "id", "athleteId", "weightClassId", "seasonId", "wonAt", "defenses"
FROM "Championship" WHERE "matchId" IS NULL;
```

Сверьте их с реальными протоколами. Для подтверждённых титулов свяжите чемпионство
с матчем завоевания и восстановите завершённые титульные матчи защит. Несуществующие
демонстрационные записи исправляйте отдельно после проверки и резервного копирования.
Произвольная привязка к ближайшему матчу недопустима. Исторические награды без протоколов
требуют отдельного решения по импорту; текущая модель не хранит происхождение их защит.

## Тесты и ограничения проверки

`npm test` запускает тесты JWT/прав, HTTP-ошибок Express 4, весов, сезонов,
сохранения/повтора/исправления/отмены результата, истории чемпионства, снимков рейтинга
и поиска `.env`. Тесты сервиса используют строгий репозиторий в памяти и не доказывают
работу PostgreSQL-блокировок.

Для интеграционного теста создайте **отдельную тестовую базу**, примените к ней обе
миграции и передайте её URL только через `TEST_DATABASE_URL`:

```powershell
$env:TEST_DATABASE_URL = 'postgresql://TEST_USER:TEST_PASSWORD@localhost:5432/kfl_test?schema=public'
npm test
```

Тест проверяет реальные записи Prisma, ограничения, пересчёт и откат транзакции;
фикстуры намеренно откатываются. Без `TEST_DATABASE_URL` он явно пропускается.
Не указывайте рабочую базу. Конкурентные запросы под нагрузкой следует отдельно
проверить на тестовом PostgreSQL перед публикацией.
