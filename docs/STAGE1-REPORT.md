# KFL — отчёт по этапу 1

Исправления внесены в проект. Исходники публичного сайта и админ-панели не менялись.
Существующие URL и JSON-контракты сохранены; дополнительно введён административный
`DELETE /api/admin/matches/:id/result` для отмены результата.

## Исправления

- Корректный разбор Bearer, проверка подписи, issuer, HS256, срока действия,
  структуры пользователя и роли. Удалён небезопасный запасной JWT-секрет.
- Победитель и метод сохраняются в Match, счёт — в MatchScore без посторонних полей.
- История чемпионства пересчитывается из завершённых титульных матчей. Повторное
  сохранение не увеличивает защиты; исправление и отмена пересчитывают последующую историю.
- Счёт, результат, чемпионства, рейтинг, снимки, уведомление и аудит изменяются
  одной транзакцией. Записи результатов одной категории сериализуются блокировкой её строки.
- При отмене удаляются устаревшие строки рейтинга; исправление старых результатов
  обновляет снимки последующих событий. Повторное сохранение не сбрасывает previousRank.
- Новый сезон всегда деактивирует предыдущий в транзакции, независимо от endsAt.
  Добавлены блокировка переключения и SQL-индекс для единственного активного сезона.
- Весовая категория выбирается по минимальному допустимому верхнему пределу;
  отсутствие категории возвращает 400. Одобрение заявки защищено блокировкой строки,
  создание спортсмена и аудит входят в одну транзакцию.
- Все асинхронные маршруты Express 4 передают ошибки централизованному обработчику.
  Неожиданные ошибки не раскрываются клиенту.
- Исправлены production entrypoint и загрузка корневого .env. Добавлены команды проверок.

## Оставшиеся ограничения

1. Локальный PostgreSQL и TEST_DATABASE_URL недоступны. Не проверены применение
   миграций, реальные транзакции/блокировки и конкурентные запросы на PostgreSQL.
   Интеграционный тест подготовлен и явно пропущен, а не объявлен успешным.
2. Корневой `.env` не создан: нужны реальные настройки владельца. API health проверяет
   только HTTP-процесс, поэтому его успех не подтверждает подключение к базе.
3. Старые чемпионства без `matchId` требуют сверки с протоколами. Если в той же
   категории есть завершённые титульные матчи, изменения возвращают 409 с откатом;
   исторические записи не удаляются и не угадываются автоматически.
4. Если в существующей базе несколько активных сезонов, администратор должен выбрать
   действующий до применения уникального индекса. Для базы без истории миграций
   требуется сверка схемы и baseline, описанные в `STAGE1.md`.
5. Незавершённые разделы админки и прочие задачи интерфейса остаются вне этапа 1.

Seed, destructive reset и изменения данных существующей базы не выполнялись.
Порядок дальнейших действий приведён в [инструкции](STAGE1.md).
