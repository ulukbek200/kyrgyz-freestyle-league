# KFL — этап 2: локальная PostgreSQL и проверка API

## Итог

Локальная PostgreSQL запущена, обе миграции применены и сверены с файлами.
Полный основной сценарий API, конкурентные запросы и откаты проверены на реальном
PostgreSQL. Backend готов к разработке интерфейсов уже реализованных операций.
Для полной административной панели потребуются дополнения API из таблицы ниже.

Публичный дизайн, компоненты и стили админки не менялись. Деплой, migrate reset,
destructive seed и изменения реальных данных не выполнялись.

## Окружение и подключение

- Найдены PostgreSQL **17.6** и PostgreSQL 18 в `C:\Program Files\PostgreSQL`.
  Существующие службы отвечали на 5432 и 5433. Они не использовались для миграций или тестов.
- Docker не найден. Использованы установленные бинарные файлы PostgreSQL 17;
  установка нового сервера не потребовалась. Версия 16 из Docker Compose не запускалась.
- Создан отдельный кластер: `127.0.0.1:55432`, только loopback, аутентификация SCRAM.
- Данные: `.local/postgres-data`. Эта папка сохраняется между перезапусками и исключена из Git.
- База: `kfl_stage2_test`; выделенная роль приложения `kfl_test_user` без superuser.
- Перед миграциями проверены адрес, имя базы, порт, метка `KFL_LOCAL_TEST_ONLY` и пустота схемы.
- Корневого `.env` не было; создан новый. `DATABASE_URL` и `TEST_DATABASE_URL` указывают
  на выделенную локальную базу. JWT-секрет создан случайным образом. Значения секретов
  не приводятся в отчёте. Существующие секреты не заменялись.
- Загрузчик `apps/api/src/env.ts` корректно читает корневой `.env`; это подтверждено
  подключением Prisma, API-тестами и регрессионным тестом из разных рабочих директорий.
- При финальной проверке PostgreSQL продолжал работать; соединение подтверждено.
  Кластер не зарегистрирован как Windows-служба и не запускается автоматически после перезагрузки.

Команды из корня проекта:

```powershell
# После перезагрузки компьютера:
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/local-postgres.ps1 -Action start

# Проверка / остановка только собственного кластера:
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/local-postgres.ps1 -Action status
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/local-postgres.ps1 -Action stop

npm run db:local:check
npm run db:local:verify
npm test
npm run test:integration
npm run test:browser
```

`-Action init` предназначен только для первого создания: при существующем `.env`
или каталоге данных скрипт откажется их перезаписывать. Для другого пути PostgreSQL
при первой настройке предусмотрен `-PgBin`.

Секрет администратора кластера хранится в `.local/postgres-admin-password`;
учётные данные отдельного **тестового** администратора сайта — в `.local/browser-admin.json`.
Не публикуйте `.local` или `.env`. Тестовый администратор создаётся без seed и без
сброса чужих паролей. Эти учётные записи не предназначены для production.

В ограниченной Windows-песочнице некоторые проверки Node/pg_ctl требуют расширенного
доступа. Финальные проверки выполнялись с разрешённым доступом и временными
`NODE_OPTIONS=--preserve-symlinks --preserve-symlinks-main`. В обычном терминале
пользователя эти обходные флаги обычно не нужны.

## Prisma и данные

Применены:

1. `202610120001_baseline` — исходная схема в новой пустой базе.
2. `202610120002_single_active_season` — частичный уникальный индекс активного сезона.

Проверены успешное завершение миграций, SHA-256 файлов против `_prisma_migrations`,
наличие SQL-индекса и `prisma migrate diff`: **No difference detected**.
Prisma diff не описывает частичные индексы полноценно, поэтому индекс проверен отдельно.
Новые изменения моделей/миграции в этапе 2 не потребовались.

`npm run db:local:deploy` разрешает миграции только на проверенной локальной тестовой
базе и отказывается применять baseline к неизвестной существующей схеме.
Для остальных баз эти тестовые команды намеренно непригодны.

Интеграционные HTTP-тесты создают синтетические данные с уникальными префиксами и
сохраняют их для просмотра. Уведомления и записи об ожидаемых ошибках тоже тестовые.
Регрессионный PostgreSQL-тест откатывает свои фикстуры. Временный триггер имитации
ошибки уведомления удалён; отсутствие оставшихся тестовых триггеров проверено.

HTTP-сценарии:

1. Вход администратора, получение JWT, защищённый dashboard, неверный пароль,
   отсутствующий/неверный/просроченный токен — 401, роль ATHLETE — 403.
2. Создание сезона с автоматической активацией, деактивация предыдущего,
   сохранение текущего сезона при ошибке создания нового.
3. Конкурентное создание сезонов: остаётся ровно один активный.
4. Создание категорий, публичная заявка, два одновременных одобрения без дублирования
   спортсмена; для 60 кг выбирается категория 65 кг.
5. Отсутствие подходящей категории: 400, заявка остаётся PENDING, спортсмен не создаётся.
6. Создание события, титульного матча и матча защиты.
7. Запись победителя/метода/счёта, рейтинг и чемпион; повтор первого результата — 0 защит.
8. Три одновременных сохранения защиты: итог ровно 1 защита.
9. Изменение старого победителя: пересчёт цепочки титулов и рейтингов.
10. Поздняя ошибка аудита: матч, счёт, рейтинг, чемпионство и уведомление откатываются.
11. Отмена результатов: возвращение предыдущего чемпиона, удаление счёта и устаревших
    рейтингов; повторная отмена корректна.
12. Поздняя ошибка аудита ручного создания спортсмена: спортсмен не остаётся в базе.
13. Ошибка создания уведомления: публичная заявка полностью откатывается.

Браузерный тест использует установленный Microsoft Edge и отдельные порты API 4400 /
frontend 5175. Сервер на 4000 уже работал и не останавливался. Временные тестовые
серверы и браузер завершаются после проверки. Встроенный Browser оказался недоступен
из-за ошибки среды, поэтому применён Playwright без загрузки дополнительного браузера.

Проверены появление административного интерфейса после входа, наличие JWT, кнопка
Sign out, удаление `nwl-token`, сохранение выхода после reload и 401 без токена.
Это **локальный выход**: ранее скопированный JWT не отзывается сервером и действует
до истечения срока. Endpoint отзыва сессий пока отсутствует.

## Обнаруженные ошибки и исправления

1. Интеграционный тест выявил частичную запись при ручном создании спортсмена:
   ошибка `AuditLog` возвращала 500, но спортсмен уже был сохранён.
   Создание спортсмена и аудит объединены в одну транзакцию; повторная проверка прошла.
2. Аналогичная граница транзакции отсутствовала между публичной заявкой и уведомлением.
   Обе записи объединены; откат подтверждён имитацией реальной ошибки PostgreSQL.
3. Первоначальный браузерный запуск столкнулся с занятым портом 4000 и таймаутом
   `tsx watch` в тестовом процессе. Тесты переведены на отдельные порты и прямой
   запуск API без watcher. Это изменение тестового окружения, не дизайна приложения.

Ожидаемые 500 в негативных тестах связаны с намеренно вызванными ограничениями БД.
Клиенту возвращается общее сообщение, секреты/внутренние детали не раскрываются.

## Готовность административных операций

Таблица сочетает реально проверенные выше сценарии с обзором существующих маршрутов.
Она не означает, что каждый перечисленный endpoint покрыт отдельным HTTP-тестом.

| Область | Что backend уже поддерживает | Что нужно для полной админки |
| --- | --- | --- |
| Авторизация | POST `/api/auth/login`, JWT, ADMIN-доступ | Управление пользователями/ролями, смена пароля, отзыв сессий; ограничения попыток входа |
| Обзор | GET `/api/admin/dashboard`, агрегированные счётчики | Истинная статистика по месяцам для графика: текущий frontend-график демонстрационный |
| Спортсмены | GET/POST `/api/admin/athletes`, PATCH статуса, nickname и категории | Полное редактирование профиля, клуба/тренера, фото; улучшение валидации пагинации |
| Заявки | Публичная подача, GET admin-списка, PATCH статуса/заметок, автоматическое создание спортсмена | Полная карточка заявки и UI заметок; правило для изменения APPROVED обратно в REJECTED (спортсмен сейчас не деактивируется автоматически) |
| Категории | GET списка, POST `/api/admin/weight-classes` | Редактирование/архивирование, правила доступности категорий по сезону |
| Сезоны | GET списка, POST нового с атомарной активацией | PATCH существующего, отдельная активация архивного, закрытие/архивирование |
| События | GET `/api/events`, POST `/api/admin/events` | Редактирование, отмена/архивирование; отдельная карточка события |
| Схватки | GET списка/карточки, POST создания, POST результата, DELETE результата | PATCH расписания/участников, перевод LIVE/CANCELLED, фильтр eventId; проверка согласованности сезона события и весов участников |
| Рейтинги | GET по сезону/категории, пересчёт при результате; GET/PATCH ranking-rule | Пересчёт существующих рейтингов сразу при изменении правил; явная операция пересчёта/история снимков для администратора |
| Чемпионы | GET действующих, автоматическая история и защиты по матчам | Отдельный административный просмотр истории и процедура сверки старых записей без matchId |
| Медиа | Только GET опубликованных материалов | Создание, редактирование, публикация/снятие с публикации и управление файлами |
| Клубы, тренеры | Модели и создание из одобряемой заявки | Справочники и отдельные CRUD endpoint |
| Уведомления и аудит | Запись в БД | Административные endpoint чтения, фильтры, отметка уведомлений прочитанными |
| Спонсоры/настройки | Модель Sponsor, отдельная настройка правил рейтинга | API управления спонсорами и остальными настройками |

Дополнительно: уникальные конфликты (например, повтор имени сезона) пока возвращают
общий 500. Для удобной админки нужны предметные 409/400. Создание схватки пока не
проверяет все бизнес-связи между событием, сезоном, статусом и категориями участников.
Это ограничения контракта, выявленные обзором кода; в этапе 2 он не расширялся.

Без изменения backend можно реализовать формы создания категорий, сезонов, событий
и матчей; ввод/исправление/отмену результата; таблицы рейтингов/чемпионов; текущие
формы управления спортсменами, заявками и правилами рейтинга. Семь разделов админки
Seasons / Events / Bouts / Rankings / Champions / Media / Settings пока являются
заглушками; готовность backend различается по таблице выше.
